## 3. Полезные решения, принятые для объединённой системы

**Отделение популяционной смертности от диагноза.** Маркер может быть связан со смертью в общей популяции без заболевания как условия включения. Для такого утверждения нельзя придумывать диагноз из поискового запроса. Условия включения, диагностический исход и причина смерти должны оставаться разными полями.

**Отдельный тип для качества моделей.** HR/RR/OR описывают ассоциацию, AUC/C-index — ранжирование, параметры калибровки — соответствие вероятностей частотам, Brier — общую ошибку вероятностного прогноза, net benefit — последствия конкретного решения. Рост качества совместного блока не приписывается его отдельным компонентам. Клиническая шкала, диагностический алгоритм и лабораторный аналит — разные сущности. Методологическое основание: [S1–S3].

**Три маршрута поиска.** Причина → заболевание → измерение; популяционная смертность → измерение; кандидат → обратная проверка исходов. Это контроль полноты поиска, а не три независимые репликации. Перечитывание заданного PMID сохраняет происхождение и не считается независимым обнаружением. Число PMID также не доказывает независимость когорт.

**Раздельная готовность.** Сохранение записи, проверка текста источника, сопоставимость, подтверждение на когорте, аналитическая пригодность измерения и клиническая полезность имеют разные статусы. Недостаточная документация блокирует соответствующее использование, но не уничтожает исходную запись.

**Теории старения — основание для гипотез, не вес риска.** Схема T → L3/L2/L1 из README полезна для организации поиска. Связь маркера с теорией не создаёт численного коэффициента и не подтверждает диагностическую полезность. Лабораторная очередность TNF-α/IL-6/GDF15 и доказательная очередность модели смертности остаются раздельными.

## 4. Воспроизведённые замечания к коду

### 4.1. Численная проверка допускает потерю знака и незаявленное изменение масштаба

`tools/mortality_graph/panel_performance.py`, `validate_performance`: поиск чисел удаляет знак и сравнивает `abs(value)`, а также `abs(value)*100` и `abs(value)*1000` с любым числом цитаты. Изолированный тест показывает: при цитате `delta C = -0.01` извлечённое `+0.01` проходит эту проверку; при цитате `delta C = 4` проходит `0.004` без явного указания масштаба.

Это **дефект первой численной проверки**, не доказательство принятия ошибочного вывода всей системой: последующая семантическая проверка upstream ещё имеет статус pending. Исправление в нашем слое: знак сохраняется, `%` и промилле допускаются только с объявленным преобразованием; сопоставляется отдельный численный фрагмент. Даже точное совпадение числа не подтверждает, что оно относится к правильному исходу или полу. Импорт старого реестра не выдаётся за повторную проверку цитат.

### 4.2. Добавочная ценность прикрепляется к неполному контексту

`panel_conference_report.py`, `_added_value`: отбор проверяет маркер, семантический статус, строку исхода и строку популяции. Горизонт, когорта, пол, возраст и метод измерения не участвуют в сопоставлении. Синтетические проверки показывают возможность выбрать показатель для другого горизонта, пола или когорты при одинаковых названиях исхода и популяции.

В новом слое автоматическое прикрепление требует совпадения исхода, популяции, страны, пола, диапазона возраста, горизонта и его основания, когорты, набора валидации, а для отдельного аналита — материала, метода и единиц. Требуется названная базовая модель. Неизвестное поле не считается совпадением. Это консервативная блокировка автоматической атрибуции, а не запрет показывать исследования разных популяций рядом с явными оговорками.

### 4.3. Половозрастная применимость теряется в сводном представлении

В `_population_rows` контекст группировки не включает пол, возрастной диапазон и страну. Сводка хранит объединённые списки применимости; проекция каждой оценки не несёт эти поля. В `final_panel` эффект превращается в строку с PMID. Две оценки из одной статьи для мужчин и женщин после такого отображения нельзя однозначно сопоставить без возвращения к исходным записям.

**Первичные записи и evidence IDs сохраняют информацию:** это потеря связи в проекциях, а не стирание всего исходного корпуса. Новый `project_estimates` переносит полный контекст с каждой численной оценкой. Формула для женщин одного возраста не может незаметно стать формулой для обоих полов всех возрастов.

### 4.4. Некорректные границы net benefit и NRI

`UNIT_INTERVAL` содержит net benefit, поэтому отрицательные значения отвергаются. Между тем для стандартного net benefit действия [S2]:

\[
NB(p_t)=TP/n-(FP/n)\,p_t/(1-p_t).
\]

Искусственный пример: n=100, TP=10, FP=40, порог 0,30. Получается **−0,07143**. Это математически допустимый отрицательный результат, а не ошибка ввода. Его отбрасывание создало бы преимущество для положительных результатов. Для интерпретации нужно хранить действие, порог и определение NB; к произвольному «риску смерти» клиническая полезность не приписывается автоматически.

Суммарный NRI — сумма двух разностей условных вероятностей [S3], поэтому его обычный невзвешенный диапазон **[−2; +2]**, а не [−1; +1]. Значение 1,2 не обязательно ошибочно. Варианты NRI должны иметь отдельное определение; они не взаимозаменяемы между исследованиями.

### 4.5. Brier ошибочно классифицирован только как калибровка

Brier перенесён в `overall_prediction_error`. Он чувствителен не только к калибровке; для проверки калибровки отдельно нужны её график, наклон, calibration-in-the-large и другие соответствующие показатели [S1]. Отрицательная разность Brier может означать улучшение, поэтому знак сохраняется.

### 4.6. Дополнительные методологические риски

Запрет популяционного утверждения по виду исходного поискового задания может снова терять корректные данные; предпочтительнее направлять их на повторную проверку области, а не выводить клиническую семантику из query. Лабораторное ограничение upstream разумно для каталога анализов, но недостаточно для общей системы риска: АД, спирометрия и функциональные тесты должны храниться отдельным типом, а не исчезать или называться белковыми маркерами.

Эти замечания не означают, что схема PR бесполезна. Напротив, разделение типов и происхождения данных существенно лучше прежнего единого списка HR; переносить следует эту архитектуру, исправив точные контракты.

## 6. Как соединяются два проекта

Предлагаемая архитектура, а не уже полностью развёрнутый продукт:

```text
aging_biomarkers: поиск A/B/C + теория как источник гипотез
    ↓ запись + источник + контекст + статус проверки
Типизированный реестр доказательств и эмпирических результатов
    ↓ экспертная оценка, сопоставимость, независимость когорт
aging_theories: совместное обучение и независимая проверка риска
    ↓ исход, горизонт, страна, пол/возраст, неопределённость
Проверка метода измерения → проспективная полезность → допустимое применение
```

Литературный граф отвечает на вопрос, что проверять; совместная статистическая модель — насколько признаки меняют прогноз на определённых данных. Ни стрелка в графе, ни HR из отдельной статьи не заменяют коэффициенты совместного обучения. Из общей смертности нельзя получать причины умножением на доли WHO.

Для будущего cause-specific слоя сохраняется модель конкурирующих рисков:

\[
\lambda_k(u|X,c,s)=\lambda_{0k,c,s}(u)\exp\{f_k(X,u,s)\},\quad
S(t)=\exp[-\int_0^t\sum_k\lambda_k(u)du],\quad
F_k(t)=\int_0^t S(u)\lambda_k(u)du.
\]

Итерация 05 не обучает эти интенсивности по причинам. Она устраняет ошибки передачи сведений, которые могли бы исказить их разработку. Замороженная NHANES-модель общей смертности остаётся отдельным историческим US-эталоном с прежними ограничениями калибровки и пола/возраста.

## 7. Воспроизведение и следующий рубеж

```bash
python -m research.mortality.build_evidence_exchange \
  --root research/mortality --out /tmp/exchange05
python -m research.mortality.pr115_regression_probes \
  --out /tmp/exchange05/pr115_audit_probes.json
python -m unittest discover -s tests -p 'test_evidence_contract.py' -v

# Полные 142 теста требуют прежних официальных файлов:
GHE_SOURCE_DIR=/path/to/who NHANES_SOURCE_DIR=/path/to/nhanes \
NHANES_RESULT_DIR=/path/to/nhanes04 python -m unittest discover -s tests -v
```

Новый код использует стандартную библиотеку Python. Зависимости прежнего NHANES-пакета и точные исходники необходимы для его интеграционных тестов. Работа без исходников не должна объявляться полным прогоном без пропусков.

Следующий проверяемый рубеж — импорт реального неизменяемого пакета конференционного прогона с идентификаторами кода/промптов, журналом исключений и обеими коллекциями записей; проверка спорных контекстов по источникам; затем заранее определённое сравнение панелей на новой выборке. Повторное использование уже просмотренного NHANES-теста не считается новой независимой валидацией. Строгое разделение смешанных причин и российская/немецкая калибровка остаются отдельными незакрытыми задачами.
